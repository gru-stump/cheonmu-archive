# 천무 자율 서사 시스템 설계

## 1. 목적

천령과 무영이 실제 시간의 흐름에 따라 대화하고 작은 사건을 겪는 모습을 생성하되, API 비용과 천무 정사(canon)를 사용자가 통제할 수 있는 개인용 시스템을 만든다.

생성과 검토는 로그인으로 보호된 온라인 관리자에서만 수행한다. 모든 생성물은 비공개 초안으로 시작하며, 사용자가 직접 승인한 결과만 기존 천무 아카이브 저장소에 기록하고 GitHub Pages에 공개한다.

첫 버전의 성공 기준은 다음과 같다.

- 컴퓨터가 꺼져 있어도 정기 생성과 특별일 이벤트가 실행된다.
- OpenAI와 Anthropic 중 하나를 선택해 사용할 수 있고 동시에 호출하지 않는다.
- 월간·일일·호출별 한도를 넘는 API 호출은 실행 전에 차단된다.
- 천령·무영의 말투, 관계 단계, 비밀 공개 순서와 기존 정사를 보존한다.
- 생성 결과는 사용자의 승인 없이는 정사나 공개 사이트에 반영되지 않는다.
- 승인된 결과는 기존 콘텐츠 검증을 거쳐 GitHub Pages에 공개된다.
- PC와 모바일에서 초안을 검토하고 승인할 수 있다.

## 2. 제품 원칙

### 사용자는 관찰자이자 최종 편집자다

사용자는 서사 속 제3의 인물로 참여하지 않는다. 자동으로 생성된 대화와 사건을 감상하고, 상황 씨앗을 제공하며, 수정·승인·거절을 결정한다.

### AI는 연출자 하나로 동작한다

캐릭터별 모델이 번갈아 API를 호출하지 않는다. 한 번의 생성 호출이 상황, 천령의 대사, 무영의 대사, 행동, 감정 변화와 연속성 후보를 함께 작성한다. 화면에서는 두 인물의 대화처럼 표현할 수 있지만 비용과 문맥은 단일 호출로 관리한다.

### 정사 변경 권한은 사용자에게만 있다

일상 대화와 작은 사건은 현재 관계 단계 안에서 제안할 수 있다. 부상, 임무 실패, 새 인물·기관·능력, 핵심 비밀 공개, 관계 단계 상승과 영구적인 변화는 자동으로 확정할 수 없다.

### 생성과 공개를 분리한다

승인은 서사의 정사 편입을 뜻하고, 게시는 공개 사이트 반영을 뜻한다. 게시 실패가 승인된 정사를 되돌리지 않으며, 승인되지 않은 결과는 어떤 경우에도 공개하지 않는다.

## 3. 범위

### 포함

- 본인 한 명만 사용하는 온라인 관리자
- OpenAI·Anthropic 교체형 제공자 어댑터
- 접속 시, 일일, 주간, 특별일 생성
- 수동 생성과 상황 씨앗 입력
- 대화, 일상 사건, 중대 사건 제안
- 초안 검토, 직접 수정, 부분 AI 수정, 승인, 거절과 보관
- 고정 정사, 연속성 장부, 최근 기억, 금지·피드백 기억
- 월간·일일·호출별 예산 및 토큰 통제
- 승인 콘텐츠의 GitHub 커밋과 기존 GitHub Pages 배포 연동
- 실행·비용·검토·게시 감사 기록

### 제외

- 두 캐릭터가 서로 다른 AI 세션으로 번갈아 호출되는 구조
- 사용자가 서사 속 인물로 대화에 참여하는 기능
- 승인 없는 자동 공개 또는 자동 정사 편입
- 제공자 장애나 예산 소진 시 다른 API로 자동 전환
- 방문자 로그인, 댓글, 투고 또는 실시간 공동 편집
- 첫 버전의 음성, 영상, 이미지 자동 생성
- AI가 관계 단계나 핵심 비밀 공개 시점을 독자적으로 변경하는 기능

## 4. 시스템 구조

시스템은 공개 영역과 비공개 영역을 분리한다.

```text
비공개 관리자 웹앱 (Vercel)
  -> Supabase Auth
  -> 초안·기억·일정·예산 설정 조회
  -> Supabase Edge Function 호출
  -> 활성 AI 제공자 한 곳 호출
  -> 구조 및 연속성 검사
  -> 비공개 초안 저장

사용자 승인 및 게시 요청
  -> 공개용 Markdown 변환
  -> GitHub 저장소 커밋
  -> 기존 validate/test/build 파이프라인
  -> GitHub Pages 공개
```

### Vercel 관리자 웹앱

인증된 사용자에게 오늘 현황, 초안함, 기억, 일정, 설정 화면을 제공한다. 브라우저는 공개 가능한 Supabase 식별자와 사용자 세션만 보유하며 AI 키, GitHub 쓰기 자격 증명과 서비스 역할 키를 받지 않는다.

### Supabase

- Auth: 단일 관리자 인증
- Postgres: 초안, 기억, 일정, 비용 원장, 작업과 감사 로그
- Row Level Security: 관리자 본인 외 데이터 접근 차단
- Cron: 일일·주간·특별일 작업 기동
- Edge Functions: 생성, 검증, 비용 정산과 게시 오케스트레이션
- Vault 또는 서버 비밀: 내부 서비스 호출에 필요한 비밀 저장

### AI 제공자 어댑터

OpenAI와 Anthropic 응답을 동일한 내부 형식으로 변환한다. 설정에서 활성화한 제공자 하나만 호출한다. 제공자를 변경해도 기억, 검증, 비용 원장과 게시기는 변경하지 않는다.

### GitHub 및 공개 아카이브

게시기는 승인된 결과를 기존 `src/content/` 스키마에 맞는 Markdown으로 변환한다. 최소 권한의 GitHub 자격 증명으로 콘텐츠 파일을 커밋한다. 기존 GitHub Actions가 검증·테스트·빌드 후 GitHub Pages를 갱신한다.

## 5. 생성 일정

기본 생성 정책은 다음과 같다.

- 접속 시: 마지막 생성 이후 최소 간격이 지났고 예산이 충분할 때 짧은 근황 또는 대화 한 건
- 일일: 하루 한 번 짧은 대화 또는 일상 사건 후보
- 주간: 주 한 번 비교적 긴 사건 후보
- 특별일: 사용자가 등록한 기념일과 지정 날짜에 별도 후보
- 수동: 사용자가 상황 씨앗과 함께 요청하는 생성

모든 시간 계산과 화면 표시는 `Asia/Seoul`을 기본으로 한다. 데이터베이스에는 UTC 시각을 저장한다.

작업에는 고유 실행 키를 부여한다. 같은 예약 구간과 생성 종류에 같은 키를 사용하여 스케줄러 재호출, 네트워크 재전송 또는 함수 재시작으로 인한 중복 생성을 막는다.

접속 시 생성은 페이지를 열 때마다 실행하지 않는다. 서버가 마지막 성공 생성 시각, 다음 허용 시각, 당일 호출 수와 현재 예산 상태를 확인한 뒤 필요한 경우에만 작업을 등록한다.

## 6. 생성물 종류와 권한

### 짧은 대화

현재 관계 단계 안의 일상 대화와 작은 감정 변화를 다룬다. 새로운 영구 설정을 만들 수 없다.

### 일상 사건

치료실, 귀환, 식사, 날씨, 짧은 외출처럼 기존 세계관 안에서 닫히는 사건이다. 다음 이야기에서 기억할 만한 약속이나 감정 변화는 연속성 후보로 표시하지만 승인 전에는 장기 기억이 아니다.

### 중대 사건 제안

부상, 새 임무, 임무 실패, 새 인물·기관·능력, 핵심 비밀, 관계 변화처럼 정사에 영향을 주는 내용을 다룬다. 첫 호출에서는 완성 본문 대신 사건 개요, 정사 영향, 필요한 결정과 예상 비용을 제안한다.

중대 사건은 다음 승인 단계를 따른다.

```text
사건 제안 -> 방향 승인 -> 장면 계획 생성 -> 계획 승인
-> 본문 생성 -> 최종 검토 -> 정사 편입 -> 게시
```

각 단계의 승인은 다음 단계 생성만 허용한다. 장면 계획 승인만으로 본문이 정사나 공개 콘텐츠가 되지 않는다.

## 7. 기억과 연속성

### 고정 정사

캐릭터 프로필, 말투, 호칭, 세계관, 현재 관계 단계, 비밀 공개 규칙과 확정 설정이다. 기존 천무 자료의 우선순위와 `cheonmu-story-writer` 연속성 원칙을 따른다. 생성 과정에서 자동 수정할 수 없다.

### 연속성 장부

승인된 사건, 약속, 부상과 회복 상태, 관계 변화, 미회수 복선, 반복할 상징과 세계관 층위 사실을 구조화해 보관한다.

### 최근 기억

최근 승인 대화와 사건 약 5~10건의 요약이다. 정확한 개수는 토큰 예산 안에서 조정하되 오래된 항목을 무조건 삭제하지 않고 연속성 장부에 필요한 내용을 먼저 승격한다.

### 금지·피드백 기억

거절한 설정, 반복을 원하지 않는 소재, 사용자가 고친 말투와 캐릭터 해석을 보관한다. 거절된 초안의 사건은 발생한 일로 기록하지 않는다.

### 프롬프트 조립

매 호출에 전체 아카이브를 넣지 않는다. 생성 종류와 관련 태그를 기준으로 고정 정사 중 필요한 부분, 연속성 장부, 최근 기억과 금지 기억을 선택한다. 선택한 자료의 ID와 버전을 생성 작업에 기록하여 결과를 재현하고 문제를 추적할 수 있게 한다.

### 연속성 검사

다음 항목을 자동 검사한다.

- 천령과 무영의 말투 및 호칭
- 현재 관계 단계보다 앞선 친밀감
- 시점 인물이 알 수 없는 정보의 단정
- 공개 단계 전 핵심 비밀의 명명 또는 확정
- 기존 사건, 부상, 약속과의 충돌
- 영구 설정을 일상 사건으로 몰래 도입하는지 여부
- 기존에 거절된 소재의 반복

검사 결과는 `통과`, `검토 필요`, `차단`으로 분류한다. 자동 검사는 사용자 승인을 대체하지 않는다.

## 8. AI 요청과 응답 형식

서사 엔진은 생성 목적, 분량, 현재 관계 단계, 필요한 정사와 기억, 금지 사항, 비용 한계를 포함하는 제공자 중립 요청을 만든다.

AI 응답은 최소한 다음 구조를 가진다.

- 제목과 생성물 종류
- 배경 시각과 장소
- 대화 및 서사 본문
- 감정 시작점과 도착점
- 사용한 연속성 요소
- 새 연속성 후보
- 잠재적인 정사 변경 후보
- 미회수 요소
- 자체 위험 표시

응답은 서버에서 구조 검증한 뒤 저장한다. 형식이 잘못되었거나 필수 내용이 없으면 정상 초안으로 취급하지 않는다. 원본 응답은 문제 추적용으로 제한 보관하고 공개 콘텐츠에는 포함하지 않는다.

## 9. 예산과 사용량 통제

### 기준 통화

비용 원장의 기준 통화는 USD다. KRW 표시는 관리자가 설정한 환율에 따른 참고값이며 청구서와 일치함을 보장하지 않는다.

### 제한 항목

- 결제 주기별 월간 총액
- 일일 총액
- 생성 종류별 최대 입력·출력 토큰
- 일일 호출 횟수
- 수동 생성 횟수
- 생성 간 최소 간격
- 제공자 및 모델별 단가와 단가 확인일

### 호출 전 예약

호출 전에 활성 모델 단가와 허용 토큰으로 최악의 예상 비용을 계산해 원장에 예약한다. 예약액을 포함했을 때 월간 또는 일일 한도를 넘으면 API를 호출하지 않는다. 동시에 시작된 작업도 데이터베이스 트랜잭션 또는 동등한 원자적 처리로 같은 예산을 중복 사용하지 못하게 한다.

### 호출 후 정산

제공자가 반환한 실제 입력·출력 토큰 사용량으로 예약액을 정산한다. 실패한 호출도 제공자 사용량이 확인되면 비용을 기록한다. 사용량을 확인할 수 없는 실패는 보수적인 예약 비용으로 남기고 관리자가 조정할 수 있게 한다.

### 예산 상태

- 정상: 예약 및 수동 생성 허용
- 주의: 주간 장편 사건 자동 생성 중지, 짧은 생성만 허용
- 위험: 모든 자동 생성 중지, 확인을 거친 수동 생성만 허용
- 한도 도달: 모든 AI 호출 차단

정확한 경계 비율은 관리자 설정으로 관리하며 초기값은 구현 계획에서 테스트 가능한 설정으로 정한다. 결제 주기가 바뀌면 새 원장을 시작하고 이전 기록은 보존한다.

### 추가 안전장치

- 활성 제공자 하나만 사용하고 수동으로 전환
- 단가가 없거나 관리자가 정한 유효기간을 넘으면 자동 생성 중지
- 재시도는 최대 한 번이며 재시도 전에도 새 예산 예약 필요
- 제공자 계정 자체의 결제 한도를 최종 안전장치로 사용
- 모델 변경 시 단가와 토큰 한도를 확인하기 전 예약 생성 비활성화

## 10. 관리자 경험

### 오늘

최근 생성 결과, 다음 예약, 작업 실패, 일일·월간 사용액과 남은 예산을 보여준다.

### 초안함

대화, 일상 사건과 중대 사건 제안을 상태별로 탐색한다. 원문, 자동 검사, 사용된 기억과 예상 정사 영향을 함께 확인한다.

지원 작업은 다음과 같다.

- 직접 수정
- 선택한 문단 또는 대사만 AI로 수정
- 승인 후 게시
- 승인하되 비공개 정사로만 보관
- 사유를 남기고 거절
- 삭제 대신 보관

직접 수정과 AI 수정은 버전 이력으로 남긴다. 부분 수정을 기본으로 하여 전체 재생성 비용을 줄인다.

### 기억

고정 정사, 연속성 장부, 미회수 요소, 금지·피드백 기억을 구분해 보여준다. AI가 제안한 기억은 승인된 생성물에서만 반영하며 사용자가 수정하거나 비활성화할 수 있다.

### 일정

일일·주간 시각, 최소 생성 간격과 특별일을 관리한다. 각 일정은 활성화 여부와 마지막·다음 실행 시각을 표시한다.

### 설정

활성 제공자와 모델, 단가, 토큰 한도, 예산, 환율, GitHub 게시 연결 상태를 관리한다. 비밀 값은 저장 후 다시 평문으로 표시하지 않는다.

## 11. 상태 모델

일반 초안의 상태는 다음과 같다.

```text
queued -> generating -> generated -> reviewing
  -> rejected
  -> archived
  -> approved_private
  -> approved -> publishing -> published
                            -> publish_failed
```

- `queued`: 실행 대기
- `generating`: 비용이 예약되고 AI 호출 진행 중
- `generated`: 구조 검증을 마친 비공개 결과
- `reviewing`: 사용자가 검토 또는 수정 중
- `rejected`: 정사에 편입하지 않고 피드백 사유만 보존
- `archived`: 활성 목록에서 숨기되 복구 가능
- `approved_private`: 정사에는 편입하지만 공개하지 않음
- `approved`: 정사 편입과 게시가 승인됨
- `publishing`: Markdown 생성과 GitHub 반영 진행 중
- `published`: 공개 커밋 생성 완료
- `publish_failed`: 승인 상태를 유지한 채 게시 재시도 가능

`published`는 GitHub 커밋 성공을 뜻한다. 실제 GitHub Pages 배포 결과도 가능한 범위에서 별도 상태로 추적하여 커밋 성공과 사이트 공개 성공을 구분한다.

## 12. 게시 흐름

1. 승인된 생성물의 최종 버전을 잠근다.
2. 공개 가능한 필드만 선택해 기존 콘텐츠 스키마로 변환한다.
3. 파일명, ID, 기록번호, 관계 단계, 내부 링크와 공개 금지 필드를 검증한다.
4. GitHub Contents API로 콘텐츠 파일을 커밋한다.
5. 기존 GitHub Actions의 validate, test와 build 결과를 추적한다.
6. 성공하면 공개 주소와 커밋 정보를 기록한다.
7. 실패하면 승인 원본과 정사 기억을 유지하고 게시 오류를 표시한다.

동시에 여러 게시를 실행하지 않는다. GitHub 파일 쓰기 충돌을 피하기 위해 게시 큐를 직렬로 처리한다. 이미 게시된 동일 버전은 재커밋하지 않는다.

## 13. 오류 처리

- 잘못된 AI 응답: 실패 결과로 격리하고 비용은 정산
- 시간 초과와 제공자 장애: 예산 재검사 후 최대 한 번 재시도
- 연속성 차단: 정상 초안함과 구분해 사용자의 판단 대기
- 예약 중복: 실행 키로 후속 작업을 무시하고 기존 결과 반환
- 인증 실패: 데이터나 비밀을 노출하지 않고 재로그인 요구
- GitHub 충돌: 최신 파일 상태를 다시 읽은 뒤 자동 덮어쓰기 없이 게시 실패 처리
- 빌드 실패: 커밋과 승인 기록을 보존하고 오류 로그 연결
- 부분 저장 실패: 상태 전이를 원자적으로 처리하여 승인과 기억 반영이 서로 어긋나지 않게 함

## 14. 보안

- 관리자 계정은 한 명만 허용하고 추가 가입을 기본 차단한다.
- 모든 개인 데이터 테이블에 Row Level Security를 적용한다.
- 관리자 요청은 사용자 세션을 검증하고, 예약 호출은 별도 서비스 자격 증명을 검증한다.
- AI 키, GitHub 쓰기 자격 증명과 서비스 역할 키는 서버 비밀로만 저장한다.
- GitHub 자격 증명에는 대상 저장소의 콘텐츠 쓰기 최소 권한만 부여한다.
- 내부 프롬프트, 원본 모델 응답, 비용, 비공개 정사와 감사 로그를 공개 Markdown에 포함하지 않는다.
- 로그에 API 키, 세션 토큰과 전체 인증 헤더를 기록하지 않는다.
- 초안은 보관을 기본으로 하고 영구 삭제에는 재확인을 요구한다.
- 감사 로그에는 주체, 작업, 대상, 시각, 이전·이후 상태와 실행 ID를 기록한다.

## 15. 테스트와 검증

### 단위 테스트

- 예산 예약, 정산, 해제와 결제 주기 전환
- 일일·월간·토큰·횟수 한도 경계값
- 제공자별 응답의 공통 형식 변환
- 기억 선택과 프롬프트 조립
- 연속성 규칙과 공개 금지 필드 검사
- 상태 전이와 허용되지 않은 전이 차단
- 공개 Markdown 변환과 파일명·ID 생성

### 통합 테스트

- Supabase 인증과 Row Level Security
- Cron에서 Edge Function까지의 예약 실행
- 중복 실행과 동시 예산 예약
- 잘못된 JSON, 빈 응답, 시간 초과와 제공자 오류
- 승인·거절에 따른 기억 반영 여부
- GitHub API 성공, 충돌, 인증 실패와 재시도
- 게시 후 기존 콘텐츠 검증·테스트·빌드 실행

### 엔드투엔드 테스트

- 모바일과 PC에서 로그인, 초안 검토, 직접 수정과 승인
- 상황 씨앗을 사용한 수동 생성
- 중대 사건의 다단계 승인
- 예산 위험·한도 도달 상태의 UI와 호출 차단
- 게시 실패 후 재시도와 공개 링크 확인
- 승인되지 않은 초안이 공개 사이트와 장기 기억에 나타나지 않음

### 출시 순서

1. 실제 외부 호출을 하지 않는 가짜 AI·GitHub 제공자로 전체 흐름을 검증한다.
2. 낮은 테스트 예산으로 AI 제공자 하나를 연결하고 사용량 정산을 확인한다.
3. 수동 생성만 활성화해 정사와 프롬프트 품질을 확인한다.
4. 일일 예약을 활성화한다.
5. 안정화 후 접속 시, 주간과 특별일 생성을 순서대로 활성화한다.
6. 게시기를 연결하고 첫 승인 콘텐츠의 검증·배포를 확인한다.

## 16. 운영 관측

관리자 화면에서 다음 항목을 확인할 수 있어야 한다.

- 최근 작업 상태와 실패 원인
- 제공자·모델별 호출 수, 토큰과 비용
- 예약 비용, 확정 비용과 조정 내역
- 다음 예약과 마지막 성공 시각
- 초안 승인·거절 비율
- 연속성 검사 경고 빈도
- 게시 커밋, 빌드와 배포 상태

비용 장부와 감사 로그는 일반 초안 삭제 여부와 무관하게 보존한다.

## 17. 확정 결정

- 혼합 생성: 접속 시 + 일일 + 주간 + 특별일
- 본인만 사용하는 온라인 비공개 관리자
- 모든 생성물은 수동 승인 후에만 정사 또는 공개에 반영
- 한 번의 AI 호출이 두 인물을 함께 쓰는 연출자 방식
- 사용자는 관찰자·연출자이며 서사 속 인물로 참여하지 않음
- OpenAI와 Anthropic을 지원하되 한 번에 하나만 수동 활성화
- 제공자 자동 장애 전환 없음
- Vercel 관리자 + Supabase 백엔드 + 기존 GitHub Pages 공개 사이트
- 승인된 콘텐츠는 Markdown으로 GitHub에 커밋한 뒤 기존 검증·배포 사용
- 중요한 변화는 다단계 승인, 일상 사건도 최종 사용자 승인 필요
- 호출 전 비용 예약과 계정 측 결제 한도를 함께 사용
